دى ملاحظات كيمى ان كانت صح و لا تضر اعملها ادرسها كويس الاول 
بناءً على تحليل الكود المتوفر من المستودع، إليك تقرير الباجز (Bug Report) مع تصنيفها حسب الخطورة:
🔴 باجز حرجة (Critical)
1.  تخزين كلمات المرور كنص عادي (Plain Text Passwords)
الموقع: shared/schema.ts + server/db.ts
passwordPlain: text("password_plain"), // نسخة نصية من الباسورد
المشكلة: يتم تخزين password_plain في قاعدة البيانات. هذا انتهاك صارخ لمبادئ الأمان الأساسية (OWASP Top 10). حتى مع صلاحيات "سوبر أدمن"، وجود كلمات مرور غير مشفرة يعرض جميع الحسابات للخطر في حالة اختراق القاعدة.
الحل: إزالة العمود تماماً واستخدام bcrypt فقط مع compare() للتحقق من كلمات المرور.
2.  فقدان البيانات عند ترحيل القيود (Data Loss on Migration)
الموقع: server/db.ts
IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'work_orders_work_order_id_key') THEN
DELETE FROM work_orders;  -- ⚠️ يحذف كل البيانات!
ALTER TABLE work_orders DROP CONSTRAINT work_orders_work_order_id_key;
END IF;
المشكلة: عند وجود قيد قديم، يتم حذف جميع سجلات work_orders دون سابق إنذار أو نسخ احتياطي. هذا قد يؤدي إلى فقدان بيانات هامة وغير قابلة للاسترداد.
الحل: استخدام ON CONFLICT أو إعادة تسمية القيد بدلاً من الحذف.
3.  SQL Injection محتمل في ensureSchema()
الموقع: server/db.ts
await pool.query(ALTER TABLE ${t} ADD COLUMN IF NOT EXISTS ${col} ${typ});
المشكلة: على الرغم من أن ${t} و ${col} و ${typ} تأتي من مصادر داخلية، إلا أن عدم وجود تطهير (sanitization) صريح يشكل ثغرة أمنية محتملة إذا تم حقن قيم خبيثة.
الحل: استخدام pg-format أو قائمة بيضاء (whitelist) للأعمدة والجداول المسموح بها.
🟠 باجز عالية (High)
4. عدم استخدام المعاملات (Missing Transactions)
الموقع: server/db.ts - دالة ensureSchema()
المشكلة: تنفذ ensureSchema() عشرات الاستعلامات المتتالية دون استخدام BEGIN/COMMIT/ROLLBACK. إذا فشل استعلام في المنتصف، ستبقى قاعدة البيانات في حالة غير متناسقة (partial state).
الحل: تغليف كل منطق ensureSchema() في معاملة واحدة.
5.  getOrders() بدون حد للنتائج
الموقع: server/storage.ts
async getOrders(): Promise<Order[]> {
return await db.select().from(orders).orderBy(desc(orders.createdAt));
}
المشكلة: إذا كان هناك مئات الآلاف من الطلبات، سيحاول هذا استردادها جميعاً في الذاكرة مما يؤدي إلى نفاد الذاكرة (OOM) وتعطل السيرفر.
الحل: إضافة .limit() افتراضي (مثلاً 1000) مع pagination.
6.  حد JSON كبير جداً (50MB)
الموقع: server/index.ts
app.use(express.json({ limit: "50mb" }));
المشكلة: حد 50MB يفتح الباب لهجمات DoS (Denial of Service) حيث يمكن للمهاجم إرسال طلبات ضخمة لاستنزاف موارد السيرفر.
الحل: تقليل الحد إلى 1-5MB كحد أقصى.
7.  تبعيات multer غير مستقرة
الموقع: package.json
"multer": "^2.1.1",
المشكلة: multer v2.x هو إصدار غير مستقر وغير موصى به رسمياً. قد يحتوي على ثغرات أمنية وعدم توافق.
الحل: الرجوع إلى الإصدار المستقر multer@^1.4.5-lts.1.
8.  bigint مع { mode: "number" } يفقد الدقة
الموقع: shared/schema.ts
workOrderId: bigint("work_order_id", { mode: "number" }).notNull(),
المشكلة: إذا تجاوزت قيمة workOrderId Number.MAX_SAFE_INTEGER (9,007,199,254,740,991)، ستفقد الدقة في JavaScript.
الحل: استخدام { mode: "bigint" } أو text لأرقام العمل.
🟡 باجز متوسطة (Medium)
9. try/catch واسع جداً يخفي الأخطاء
الموقع: server/db.ts
try {
// مئات الأسطر من الكود...
} catch (e) {
console.warn("phone_lines seeding/normalization skipped...", e);
}
المشكلة: هذا الـ try/catch الضخم يخفي الأخطاء الحقيقية ويجعل تصحيح المشاكل مستحيلاً. أي خطأ داخلي (حتى خطأ في بناء الجدول) سيُلغى بهدوء.
الحل: تقسيم try/catch إلى أجزاء أصغر واستخدام throw للأخطاء الحرجة.
10.  readFileSync مع مسار غير موثوق
الموقع: server/db.ts
readFileSync(join(process.cwd(), server/phone-lines-seed-${i}.json), "utf-8")
المشكلة: process.cwd() يمكن أن يتغير في بيئات الإنتاج (مثل Docker أو PM2)، مما يؤدي إلى فشل في العثور على الملفات.
الحل: استخدام import.meta.url أو __dirname لتحديد المسار النسبي.
11.  string_agg(DISTINCT ...) قد ينتج نتائج غير متوقعة
الموقع: server/db.ts
string_agg(DISTINCT tn.tech_name, ' , ')
المشكلة: دمج أسماء متعددة بفاصل ' , ' قد ينتج عنه بيانات غير صالحة للعرض أو المعالجة اللاحقة.
الحل: اختيار اسم واحد بوضوح أو تخزين الأسماء في جدول منفصل.
12.  default([]) لـ jsonb قد لا يعمل
الموقع: shared/schema.ts
days: jsonb("days").notNull().default([]),
المشكلة: default([]) في Drizzle ORM قد لا يترجم بشكل صحيح إلى '[]'::jsonb في PostgreSQL.
الحل: استخدام default(sql'[]'::jsonb) أو التأكد من الترجمة الصحيحة.
13.  reusePort: true قد يسبب مشاكل في الإنتاج
الموقع: server/index.ts
httpServer.listen({ port, host: "0.0.0.0", reusePort: true }, ...)
المشكلة: يسمح لعمليات متعددة بالاستماع على نفس المنفذ، مما قد يسبب تشتت الطلبات إذا لم يتم إدارته بشكل صحيح (مثل cluster mode).
الحل: إزالة reusePort إذا لم يكن هناك حاجة محددة له.
14.  تراكم جلسات sf_session المنتهية
الموقع: server/db.ts
CREATE INDEX IF NOT EXISTS "IDX_sf_session_expire" ON "sf_session" ("expire");
المشكلة: يوجد فهرس على expire لكن لا توجد وظيفة حذف تلقائي للجلسات المنتهية. سيؤدي هذا إلى تراكم البيانات بلا حدود.
الحل: إضافة cron job أو استخدام connect-pg-simple مع خيار pruneSessionInterval.
15.  تبعيات متكررة (bcrypt + bcryptjs)
الموقع: package.json
"bcryptjs": "^2.4.3",
"bcrypt": "^5.1.1",
المشكلة: وجود مكتبتين لنفس الغرض يزيد من حجم الحزمة وقد يسبب تعارضات.
الحل: الاحتفاظ بواحدة فقط (يفضل bcryptjs لأنه لا يحتاج native compilation).
🟢 باجز منخفضة (Low)
16. unhandledRejection يخفي الأخطاء
الموقع: server/index.ts
process.on("unhandledRejection", (reason) => {
console.error("[unhandledRejection]", reason);
});
المشكلة: يمنع الـ crash لكنه يخفي الأخطاء بدلاً من معالجتها. الأفضل هو إعادة الرمي (re-throw) بعد التسجيل أو استخدام async/await مع try/catch في كل مكان.
17.  rawBody معرف كـ unknown
الموقع: server/index.ts
declare module "http" {
interface IncomingMessage {
rawBody: unknown;
}
}
المشكلة: يتطلب أي استخدام لاحق لـ rawBody عمل type assertion، مما يزيد من خطر runtime errors.
الحل: تعريفه كـ Buffer | undefined.
18.  JSON.parse بدون try/catch
الموقع: server/db.ts
allLines = allLines.concat(JSON.parse(raw));
المشكلة: إذا كان ملف JSON تالفاً، سيحدث crash للسيرفر.
الحل: تغليف JSON.parse في try/catch.
